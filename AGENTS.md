# Watt Terminal: guide for coding agents

Watt is a terminal for macOS and Windows 11 where the user and an AI agent share one persistent shell session (`zsh -l` on macOS, PowerShell on Windows, through an integration shim). CI runs the checks on macOS, Windows and Ubuntu. Tauri v2 + Rust backend (`src-tauri/`), React 19 + TypeScript frontend (`src/`), xterm.js for rendering. `README.md` covers usage; this file covers how to change the code safely.

## Commands

- Frontend: `npm test` (vitest), `npx tsc --noEmit`, `npm run build` (tsc + vite). Run all three before calling frontend work done.
- Backend (from `src-tauri/`, with `cargo` on PATH): `cargo check` for quick feedback, `cargo clippy` (kept warning-free), `cargo test`. The integration tests in `src-tauri/tests/` spawn real `zsh -l` sessions one at a time and take minutes; run them once at the end, not in a loop. Some are `#[ignore]`d on purpose (ssh needs Docker, one needs the real Keychain).
- Run the app: `npm run tauri dev`. Build and install the macOS app: `npm run app:release -- --open` (`scripts/`, README). `app:build` runs `tsc` and `vitest` first (`--no-checks` skips them, `--full` adds clippy and cargo test).
- `scripts/*.sh` are written for macOS's bash 3.2. `bash scripts/test-app-scripts.sh` tests them with fake bundles; it needs macOS tools (`hdiutil`, `codesign`) but never launches the app.
- Rust edition 2024. Tauri crates and the `@tauri-apps/*` packages are pinned; bump them together. No formatter or linter config exists beyond strict `tsconfig` (`noUnused*`): match the surrounding style.

## Map

- `src/App.tsx` wires the panels; `src/App.css` is the only stylesheet. `src/components/` holds React components, `src/lib/` pure logic. Put decisions (layout rules, formatting, state machines) in `src/lib/` with a colocated `*.test.ts`, and keep components thin.
- Component tests use `renderToStaticMarkup` (no DOM environment is installed), so DOM-only behaviour (focus, scrolling, observers, layout) is not covered by vitest. Test that logic as pure functions and check the rest by running the app.
- `src/lib/types.ts` mirrors the Rust serde shapes (events, loaded conversations); `src/lib/api.ts` wraps the Tauri commands. Change both sides together.
- `src-tauri/src/lib.rs`: setup, plugins, commands. `core/`: `pty.rs`, `observer.rs`, `session.rs` (the shared shell), `shim/` (shell integration scripts), `inject.rs`, `foreground.rs`, `approval.rs` (policy), `tools.rs` (tool schemas and dispatch), `chat/` (agent loop, prompt, history, context budget and trim, todo, attachments, `redact.rs`, `side.rs` for the one-off side-call primitives behind `/btw` and `/compact`, `commands.rs` for the custom slash-command catalog, `instructions.rs` for the workspace-root `AGENTS.md` project instructions), `llm/` (provider requests, SSE), `settings/` (settings.json, models, presets, secrets), `persist/` (conversations, UI state), `migrate.rs`, `env.rs` (WATT_* names with legacy AGENT_TERM_* fallbacks). Slash-command parsing, templates, model matching, help/context rendering and Markdown export live in `src/lib/commands.ts`; custom templates come from `<workspace root>/.watt/commands` (project) and `<config dir>/commands` (global).
- The autocomplete menu logic lives in `src/lib/commandMenu.ts` with `src/components/CommandMenu.tsx` (owned by `InputBar.tsx`); the `/help` dialog is `src/components/HelpDialog.tsx` (opened from `App.tsx`, never written to the transcript). The image viewer is `src/components/ImageViewer.tsx` (one provider in `main.tsx`, `useImageViewer()` opens it; the size rule is `src/lib/imageViewer.ts`); a sent image's full file comes from the `get_attachment` command, never from the webview's own copy.

## MCP and skills

- `core/external_tools.rs` is the seam: the agent asks an attached `ExternalToolHost` for tool names, approval and calls. MCP plugs in there; `agent.rs` does not know about it.
- `core/fs_tools/`: the read-only file tools (`read_file`, `list_dir`, `glob`, `grep`) and the write tools (`write_file`, `edit_file`). `tool.rs` has the schemas, argument checks and the place check (this machine, a nested shell, or unknown); `scope.rs` has the project-root confinement, the sensitive-path blocklist and the write checks (no `.git`, no symlink out of the root); `write.rs` has the edit semantics, card previews and the atomic write; `local.rs` is the local backend; `backend.rs` is the trait a remote backend would implement (not built). The write tools go through the approval gate (`call_fs_write` in core/agent.rs).
- `core/mcp/`: `config.rs` (settings, names only), `secrets.rs` (values, in the secret store), `parse.rs` (paste-JSON import), `expand.rs` (`${NAME}` and transport values), `launch.rs` (stdio program), `names.rs` (`mcp__{server}__{tool}`), `approval.rs` (levels), `manager.rs` (thread handle), `runtime.rs` (the `watt-mcp` thread, the only owner of live clients), `client.rs` (connect, stderr drain), `service.rs` (what lib.rs calls; enabled servers start in the background at launch via `warm`, and `status` feeds the composer's MCP panel without starting anything), `tools.rs` and `result.rs` (schemas, result text), `logs.rs` (redacted, bounded log ring).
- `core/skills/`: `folders.rs` (the folder settings: `~`, absolute or relative to the project; normalised and deduped; refused under Watt's config/data/secrets folders and `.ssh`/`.gnupg`/`.aws` via `fs_tools` `blocked_reason`), `scan.rs` (finds `<root>/<name>/SKILL.md`; same name in a later folder is shadowed with a warning), `frontmatter.rs`, `tool.rs` (the read-only `skill` tool), `builtin.rs` + `builtin/*.md` (the built-in `watt` skill: a cheatsheet compiled in, not on disk; the name `watt` is reserved, so a folder skill of that name is ignored with a warning; always listed first, always on, never a card, not switchable; its `state` file is the live redacted snapshot from `state.rs`, built from an allowlist, so a new setting field stays out until added there; every curly-quoted UI label in `builtin/*.md` must match `src/` verbatim, checked by `src/lib/builtinSkill.test.ts`), `mod.rs` (types, settings, view). Roots: the Watt config `skills` folder first, then the configured folders (default `~/.agents/skills`, `~/.claude/skills`, `.agents/skills`, `.claude/skills`; relative ones only when the local shell is on top). Skills can be switched off by name (`skills.disabled`); the switch does not override `disable-model-invocation`. Approval: `skills.approval` (`ask` or `auto`, default `auto`), with a per-skill `skills.overrides` entry that wins. An `ask` skill shows a card (reason `skill_read`); approving it covers that skill for the rest of the turn (its files too; never saved), and a decline is an error the turn goes on from.
- Settings tabs: `src/components/McpSection.tsx` with `McpServerForm.tsx`, `SkillsSection.tsx`, switched by `SettingsTabs.tsx`. Secret values never reach the view, the settings file or the logs.

## Invariants

- The agent bar's text is a message to the agent, unless it is a registered slash command (`/help`, `/new`, `/stop`, `/model`, `/export`, `/context`, `/history`, `/rename`, `/btw`, `/compact`, `/fork`, `/plan`, `/review`, `/init`, or a custom command). `/btw` answers once and stores nothing; `/compact` and `/fork` start new conversations and switch to them atomically. `run_command` and `send_keys` need user approval unless a rule or bypass allows them (typed lines still hit the hard gate and deny rules). A denied call (any tool; `agent.on_denied`, Settings > Approvals): `continue` (the default) returns it as a `not_approved` error with guidance and the turn goes on; `stop` ends the turn with a notice. `run_command` runs only at an idle prompt with shell integration live. Read tools are always allowed. External (MCP) tools follow their server's and tool's level (Ask, Auto or Never): a Never tool is hidden from the model and refused, and approve-all runs the others without a card. The read tools (`read_file`, `list_dir`, `glob`, `grep`) are ungated; the `skill` tool is gated per skill (see the skills line). `write_file` and `edit_file` always need approval (reason `fs_write`; no saved rules), and approve-all runs them without a card only for paths inside the project folder. The file tools work only on this machine (not in a nested shell), read only inside the session's project folder, and never read the sensitive paths (private keys, `.env` files, `.ssh`/`.gnupg`/`.aws` folders, Watt's config, data and secrets files). The write tools never write `.git`, the sensitive paths, or outside the project folder (refused, not asked).
- The user's dotfiles are read, never edited: the shim runs the shell with its own `ZDOTDIR` and sources the user's files. Keep test and manual runs away from real state: `WATT_HISTFILE`, `WATT_CONFIG_DIR`, `WATT_DATA_DIR` (and `WATT_SECRETS_FILE`, a 0600 file store, instead of the Keychain). Note the integration tests do execute the user's real startup files; they only redirect `HISTFILE`.
- Secrets live in the Keychain (one item holding a JSON blob), the opt-in secrets file, and process memory (plus the dev-only `WATT_LLM_KEY`). Never put them in `settings.json`, logs, fixtures or transcripts; tool output goes through `chat/redact.rs`.
- Stored conversation history is the truth. Context trimming is wire-only and never rewrites it. Token counts are estimates (chars/4, calibrated against provider usage); with no known model limit nothing is trimmed proactively.
- Model variants are shallow request-body overlays saved per model (`Model.variants`, `ModelRef.variant`): auto-built from the provider model list (OpenRouter `reasoning.supported_efforts` → `reasoning.effort`; OpenCode `capabilities.reasoning.effort` → `reasoning_effort`) or manual JSON. Protected keys (`model`, `messages`, `stream`, `tools`, `stream_options`, `max_tokens`, `max_completion_tokens`, `models`) are rejected and skipped at merge. Side calls (`/btw`, `/compact`) never carry a variant.
- The bundle id is `dev.watt.terminal`. Legacy `dev.agentterm.app` data and Keychain items are copied at first launch and never deleted or overwritten (`migrate.rs`, `settings/secrets.rs`).
- CSP is strict (`tauri.conf.json`, `src/lib/csp.test.ts`): no inline scripts, no remote resources. Native file drop is off on purpose; drops are handled in the webview (`src/lib/dropGuard.ts`).
- A reply is discarded, never stored, when a command open at its request start finishes before the reply is acted on (`respond` and `send` in `core/chat/agent_loop.rs`, `reply_discarded` in `src/lib/transcript.ts`). Keep it so: no partial reply in the history.

## UI and layout work

- The renderer is WKWebView (WebKit), not Chrome: use `-webkit-` prefixes where needed and check layout in WebKit as well as Chromium.
- Docks are left and right; the panel can collapse to a rail (`src/lib/panelLayout.ts`: panel minimum 240px, terminal minimum 320px). The window minimum is 800x600. Check narrow and short sizes, banners on and off, and the font-size steps.
- Prefer whole-pixel sizes: fractional heights on Retina round into phantom scrollbars. Keep overflow hidden until content really overflows.
- Colours come from the tokens under `[data-theme="blueprint"]` in `App.css`. Animate only `transform`, `opacity` or `background-position`, and honour `prefers-reduced-motion`.
- Look at screenshots of the extreme sizes before trusting geometry assertions.

## Working practices

- Read the neighbouring code and reuse its helpers first. Add tests next to what you change. Change an existing assertion only when the behaviour change is intended, and say which one and why.
- Hooks run on every render, before any early `return` and never inside a condition, loop or `&&`/`?:` branch. `src/lib/hooksOrder.test.ts` checks all of `src/` for this (a hook after an early return crashed the UI in InputBar).
- Verify with real command output. Report what passed, failed, was skipped and remains unverified; never claim a check passed without running it.
- Keep changes scoped: no drive-by refactors, no new dependency without a reason, no loosening a check to get green.
- Commit small, with imperative messages that explain the why. Don't commit `dist/`, `src-tauri/target/` or local task notes.
